# External test corpus: biogas digestion (Middleton Digester)

One SOP for a fictional anaerobic digestion / biogas utilisation facility.

## Construction

Generated 2026-07-22, the **first** of the three external corpora and the only
one whose generating prompt was **not retained**. Its protocol differs from the
other two in one material respect, recorded under "Priming" below.

- Generated by **DeepSeek-V4-Pro** — a different model family from the
  `gemma4:31b` the extraction pipeline runs on, so the documents cannot be
  idiomatic to the model that reads them.
- **The domain was the generator's own choice.** The prompt asked for an
  industry other than the development corpus's production line and did not name
  one; anaerobic digestion was selected by the generator.
- Procedures as `.txt`, annotation as one `.csv` with one row per rule. Class
  vocabulary, identifier convention, layout and granularity were the
  generator's own.
- Document and annotation were produced in the **same generation pass**, so the
  annotation is not an independent reader of the document. This is declared in
  the thesis (§How the External Corpora Were Constructed, §The External Corpora
  Were Not Equally Held Out).
- Generated **once** and kept **as delivered**. No corpus was regenerated or
  discarded, so there was no selection among candidate test sets.
- **Not read before the first scoring run.** Nothing was inspected against
  pipeline behaviour before being measured.
- No repairs. The annotation is byte-identical to what was delivered.

## Priming: this corpus saw the development schema

Unlike the desalination and sulfuric acid prompts — both retained verbatim in
their own READMEs — the biogas prompt **described the development corpus's
ground-truth structure to the generator as a model of what was wanted**. It did
not dictate column names, but it did not withhold them either.

The annotation shows it. Set against the development schema:

| Development corpus | Biogas |
|---|---|
| `ruleId` | `id` |
| `class` | `category` |
| `station` | `asset` |
| `sensor` | `tag` (present but **empty on every row**) |
| `sensorType` | `parameter` |
| `condition` | `condition` |
| `action` | `action` |
| `severity` | `severity` |
| `critHi, warnHi, critLo, warnLo` | `bound_low, bound_high` |
| `unit` | `unit` |
| `source` | `source` |

Five column names (`condition`, `action`, `severity`, `unit`, `source`) carry
over verbatim, and the mapping is otherwise one-to-one. The empty `tag` column
is the clearest tell: the development corpus distinguishes a station from the
sensor on it, this facility does not, and the generator kept a slot it had no
use for.

**Consequence.** Biogas is *less* independent of the development corpus than the
other two externals, in precisely the dimension — schema independence — that the
transfer claim rests on. The later desalination prompt bans
`station, sensor, sensorType, critHi, warnHi, critLo, warnLo` by name; that ban
is a response to this leak.

What the leak does **not** touch: the domain, the document, the class
vocabulary, the identifiers, the granularity, and the numbers were all the
generator's. The pipeline is never given any schema at run time, so the priming
affects how demanding this corpus is, not whether the measurement is honest.

## Reconstruction of the prompt — NOT the original

The original was not saved and is not recoverable from any transcript. What
follows is reconstructed from the delivered artifacts and the author's
recollection. **It is not evidence of what was run** and should not be cited as
the prompt.

```
I'm building a test set for an information-extraction system.

I already have a development corpus: a set of plain-text standard operating
procedures for a bottling / packaging production line, plus a ground-truth CSV
annotating every rule they state. The ground truth has one row per rule, with
columns for the rule's identifier, its class, the equipment and measurement it
concerns, the condition, the required action, a severity, the numeric warning
and critical bounds, the unit, and the source document.

I want a second corpus in the same spirit, for a completely different industry,
so I can test whether the system generalises beyond the domain it was built on.

Pick any process industry other than a bottling / packaging production line --
whichever you think makes the better test -- and produce:

1. One plain-text SOP for that facility, written the way that plant would
   actually issue it: title and revision block, numbered sections, a purpose
   and scope section, tables where tables fit, prose where prose fits. Give it
   normal operating limits with units, automated control and alarm responses,
   maintenance and calibration triggers, and access or safety restrictions.
   Use realistic numbers throughout. Around 40-50 rules.

2. A ground-truth CSV annotating it, one row per rule. Use whatever columns
   suit this document and this industry. Every rule stated in the document must
   appear, and nothing may appear that the document doesn't state.

Give me the .txt and the .csv, nothing else.
```

Recoverable from the artifacts: one document, generator-chosen domain, ~40–50
rules, dev schema shown, no printed-identifier requirement. Not recoverable:
the exact wording, and whether any granularity instruction was given.

## Files

- `SOP_BDG_003_MiddletonDigester.txt` — the procedure.
- `ground_truth_biogas.csv` — 47 rows, 12 columns
  (`id, category, asset, tag, parameter, condition, action, severity,
  bound_low, bound_high, unit, source`).

## Conventions this annotation chose for itself

- Identifiers `R01`–`R47`, invented by the annotator; they appear nowhere in the
  document, so identifier agreement is zero for any extractor.
- A 9-value `category` vocabulary of its own (`NormalOperatingLimit`,
  `AlarmControlResponse`, `MaintenanceTrigger`, …) unrelated to the development
  corpus's four classes.
- Bounds named `bound_low` / `bound_high`.
- Granularity: one printed table row is split into two annotated rows, one for
  the limit and one for the triggered response.
