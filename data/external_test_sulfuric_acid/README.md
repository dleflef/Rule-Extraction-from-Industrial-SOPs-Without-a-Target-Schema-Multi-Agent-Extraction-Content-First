# External test corpus: sulfuric acid plant (SAP2) — added 2026-08-07

Three SOPs for one fictional contact-process sulfuric acid plant, generated by
**DeepSeek-V4-Pro** — a different model family from the `gemma4:31b` the
extraction pipeline runs on. The annotation chose its own columns; no schema was
imposed, and the domain was the generator's choice from outside a four-item
exclusion list.

The prompt did more than fix the container format, and the verbatim text is
below so the reader can judge rather than take the summary on trust. It
specified the identifier convention (`R001, R002, ...`) and gave an explicit
**granularity instruction** — stated as a document-intrinsic standard ("follow
the documents' own granularity"), but given nonetheless, and disclosed in the
thesis for that reason.

Same protocol as the other two external corpora: document and annotation from
the same generation pass, generated once and kept as delivered (no regeneration,
no discarding, no selection among candidates), and not read before the first
scoring run.

## The generating prompt, verbatim

```text
I need two things for an information-extraction benchmark: a set of industrial
operating documents, and a complete annotation of the rules they state.

=== PART 1: THE DOCUMENTS (2 or 3 plain .txt files) ===

Invent one industrial facility and write 2-3 standard operating procedure /
control documents for it, each covering a different aspect of its operation.

Pick any process industry EXCEPT these four, which are already covered:
discrete factory production lines, biogas / anaerobic digestion, semiconductor
cleanrooms, and seawater desalination.

- Write them like real internal documents that plant would issue: title block,
  revision history, numbered sections, the operational content that facility
  actually needs.
- Lay out each section however that particular content is naturally laid out.
  Use a table where a table is the natural form, prose where prose is natural,
  bullets where bullets are natural. Mix freely, and vary it between documents.
  Do not impose one uniform style, and do not feel obliged to use any
  particular device -- if a section reads best as four paragraphs of narrative
  with the numbers inline, write it that way.
- Cover the kinds of content such documents carry: numeric limits and setpoints
  with units, automatic responses to conditions, who is permitted to do what,
  scheduled maintenance and calibration, handover and logging duties -- or
  whatever else genuinely fits the facility you invent.
- Use real, varied numbers: thresholds, tolerances, intervals, durations,
  counts, pressures, temperatures, with units.
- 40-70 distinct rules across all documents combined.
- Plain text. Light markdown is fine if that is how you would naturally lay it
  out. Name them SOP_<code>_<topic>.txt.

=== PART 2: THE ANNOTATION (one .csv) ===

One row per rule stated in the documents.

- CHOOSE YOUR OWN COLUMNS. Use whatever fields best capture the rules in THESE
  documents -- as many or as few as they need, named however you find natural.
  There is no target schema and you should not try to guess one. Do not force
  every rule into columns that only suit some of them.
- Include one column with a unique key on every row (R001, R002, ...), and one
  naming which document each rule came from.
- COMPLETENESS IS THE MOST IMPORTANT PROPERTY. Every rule the documents state
  must appear. Follow the documents' own granularity: if the document states
  something separately, annotate it separately. A table with 30 data rows is 30
  rules. A grid crossing 5 subjects with 6 cases states 30 separate rules, one
  per cell, because each cell states what applies in its own case and nothing
  about the others -- not 5 rules. A paragraph stating four requirements is
  four rows. Do not summarise, group, or skip anything for being repetitive.
- FAITHFULNESS IS SECOND. Every row must be supported by text actually printed
  in the documents. Do not add rules that are implied, standard industry
  practice, or reasonable but unwritten.
- Copy values exactly as the documents print them: same numbers, same units,
  same spelling of identifiers. Do not convert, round, or normalise.
- Quote/escape properly so the CSV parses cleanly (rule text will contain
  commas).
- Name it ground_truth_<tag>.csv.

Do not explain your extraction logic, do not provide a field dictionary, and do
not add commentary. Just the files.
```

Two instructions were deliberately withheld: nothing told the generator to keep
hyphens and Unicode consistent between document and annotation, or to avoid
blank cells. Real documents carry those inconsistencies and the evaluator is
built to absorb them; sanitising them away would have made the test easier than
reality.

- `SOP_SA_OP_002.txt`, `SOP_SA_ESD_005.txt`, `SOP_SA_MNT_008.txt`
- `ground_truth_SA.csv` — 70 rows, the annotation AS DELIVERED (headline GT).
  Five rows (R045/R046/R049/R050/R058) arrived with one surplus empty field
  each, which made the file unparseable; the empty overflow was truncated to
  the 10-column header. No value was altered.
- `ground_truth_SA_rowlevel_DIAGNOSTIC.csv` — 49 rows. NOT the ground truth.
  A diagnostic in which the two ATTRIBUTE tables the annotation split
  cell-by-cell are regrouped to one row per table row: Table 1 thresholds
  (R012-R023 -> 3) and the Table 2 trip scenarios (R036-R051 -> 4). Used only
  to measure how much of the headline score is annotation granularity rather
  than extraction quality. Report the 70-row figure as the result.
